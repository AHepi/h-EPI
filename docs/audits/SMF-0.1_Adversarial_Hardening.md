# SMF-0.1 adversarial hardening record

## Scope

This record preserves attacks made while building the Semantic Model Forge kernel. It is an engineering audit of failure modes and repairs, not a semantic validation of CR-1.0, the seed oracles, the weak typed-role fixture, or the proposed mathematical target. A passing regression means only that the named exploit was not reproduced against the tested implementation and frozen inputs.

## Attacks retained as regressions

| Attack | Original weakness | Fail-closed repair | Current regression surface |
|---|---|---|---|
| Status laundering | Caller-supplied references could appear to license positive hardening or readiness. | Status is recomputed; plain strings cannot resolve typed gain, preservation, review, or decision obligations. The current kernel cannot emit `HARDENING_UNREFUTED` or `PROVISIONALLY_READY`. | Hardening/readiness parser and constructor tests; calibration semantic-field mutation tests. |
| Authority-scope rewrite | A canonical run could retain its general shape while authority meaning or scope text was altered. | Authority identity, digest, byte count, page count, status, dimensions, semantic scope, and verification scope are exact runtime constants; full report replay is byte-exact. | Calibration loader/replay tests and semantic/status fuzz matrix. |
| Partial run identity | A saved report did not initially bind every executable fixture, evaluator, corpus byte, challenge record, schema, and implementation file that determined it. | The run contract hashes the exact corpus bytes, complete challenge and fixture contracts, candidates, revisions, evaluators, implementation code, and every registered forge schema. Replay refuses any drift and regeneration is compared exactly. | Calibration contract-drift, report-regeneration, normal/optimized invariance, and no-clobber tests. |
| Schema-only false assurance | Generic JSON Schema success could be described as mechanical validation even when cross-record hashes or semantic invariants were unchecked. | The validation CLI invokes specialized runtime validation where available and distinguishes `SCHEMA_AND_RUNTIME_VALID` from `SCHEMA_VALID_ONLY`. | Validation-CLI tests tamper a research report and calibration human-review meaning. |
| Runtime scope selected by filename | A custom schema could reuse a registered schema filename while declaring a different `$id`, causing the validator to overstate specialized runtime coverage. | Runtime scope is selected only by the canonical registered `$id`; same-filename schemas with another identity remain schema-only. | Custom same-filename/different-`$id` validation-CLI test. |
| Context-free plan assurance | A self-rehashed plan could change its route, reason, limits, or question bindings and still look valid without replaying its origin. | Intrinsic validation fixes non-inductive fields and route/triage coherence; the append CLI additionally regenerates the complete plan from the exact run, ledger, and origin head. Generic validation explicitly reports only `INTRINSIC_RECORD_ONLY`. | Self-rehashed route/question attacks, intrinsic-scope reporting, and stale-plan CLI tests. |
| Source-reference borrowing | A plausible identifier or locator could be copied onto a different corpus subject and presented as source-grounded. | Every `CR1REF` resolves to an enumerated source record and binds subject digest, relationship, basis kind, locator, pages, use, and the pinned identifier inventory. | Corpus mutations cover fabricated IDs, borrowed IDs, source ID, locator, page, use, subject, and authority promotion. |
| Interpretation-to-authority promotion | Provisional paraphrases near source anchors were labeled `source_authority`. | Unreviewed seed claims are `source_interpretation` with `interpretation_provisional`; the seed contains no reviewed source-authority annotation. | One-to-one annotation and provenance-shape tests. |
| Annotation-prose authority laundering | An editorial title or boundary note could make an authoritative claim while leaving typed reference fields unchanged. | Every annotation marks that prose `unreviewed_non_authoritative` with semantic effect `none`; schemas and runtime enforce the boundary. Prose changes cannot select an evaluator or alter claim status. | Missing, promoted-status, promoted-effect, and arbitrary-prose corpus tests. |
| Untyped dynamic oracle | A newly constructed challenge could carry an arbitrary free-text oracle even though seed-corpus oracles had typed annotations. | Runtime and schema require every oracle to declare an explicitly non-final status and a rationale; built-in dynamic templates are `project_import_provisional`, and no standalone challenge acquires source authority. | Dynamic-oracle status parser, schema, and generated-template tests. |
| Research-report adoption | A source summary and its proposed engineering use could be conflated, allowing the report to self-authorize a model change. | Ledger v2 stores only bounded source-claim reports. Project use is a separate digest-bound `PROPOSED` record; engineering decisions are human-scoped and the seed has none. | Research-ledger separation, adoption, oracle, promotion, and digest tests. |
| Unauthenticated decision adoption | Merely writing `decision_maker_role: HUMAN_REVIEWER` could create an operative engineering decision. | Ledger v2 rejects every nonempty engineering-decision collection until a trusted attestation mechanism exists. | Decision-injection runtime and schema tests. |
| Provider oracle | AlphaXiv ranking, provider summaries, agreement, or source counts could enter semantic status. | AlphaXiv is a replaceable discovery default. Retained reports require exact-version primary inspection; provider outputs, agreement, rank, and count have no promotion field. | Provider-policy and promotion-switch tests. |
| Provider lock-in disguised as replaceability | Schemas and planners hard-coded AlphaXiv while policy claimed that the provider was replaceable. | Generic schemas accept any nonempty provider label; the planner derives its current default from the bound policy and requires the run warrant and ledger to agree. The present data still selects AlphaXiv. | Re-versioned-corpus provider test, ledger replacement test, and plan binding checks. |
| Research from any failure | A failed test could automatically trigger external search, silently assuming the failure locus. | Adaptive inquiry requires separately supplied, content-addressed human locus assessments plus an explicit scheduling action. No triage yields `AWAITING_HUMAN_TRIAGE`; assessments without an action yield `AWAITING_HUMAN_ACTION_SELECTION`; both produce zero questions and a null verdict. | Live no-triage, no-action, and route-matrix tests. |
| Exclusive-locus collapse | A failed conjunction was forced into exactly one of candidate, auxiliary, test, scope, or unresolved, erasing coexisting and joint criticisms. | Active v2 triage retains multiple `LIVE` assessments, and one assessment may name several loci. `UNRESOLVED` is overall status only; every assessment is criticism rather than an established cause. Exclusive v1 records remain historical. | Concurrent-locus, joint-mechanism, local-`UNRESOLVED`, permutation, and content-address tests. |
| First-locus or count-based routing | Array order, number of diagnoses, or an implementation precedence rule could silently choose what to do and appear to rank semantic plausibility. | Diagnosis and scheduling are separate. One nullable content-addressed `next_action` records only a human scheduling choice; no action fails closed. Selection bases are limited to dependency order, shared work, or explicit human priority. | Reordered-assessment, independent-frontier, normal/optimized parity, and self-rehashed-route tests. |
| Dependency bypass | A downstream criticism could be selected while a live prerequisite remained unexamined. | Assessment dependencies are exact, acyclic, and canonical; selected assessments must lie on the dependency frontier. Unknown, duplicate, self, cyclic, and blocked edges fail after rehashing. | Dependency-graph and blocked-action tests. |
| Scope veto | Merely recording a possible boundary problem could short-circuit simultaneous candidate, auxiliary, or test criticism as globally `OUT_OF_SCOPE`. | `SCOPE` is one live locus, not a closure state. It can criticize either case membership or the boundary itself; routing follows only the selected compatible action. | Mixed-scope routing and forged-`OUT_OF_SCOPE` plan tests. |
| Broad research authorization | An external-looking assessment could unlock every falsifier in the case or substitute a familiar issue or warrant. | External actions bind one exact issue and warrant by ID and digest. Questions also bind the action and selected assessments, and retain exact rivals, falsifiers, source scope, and stop rule. | Exact-research-target, unselected-locus, question-binding, and substitution tests. |
| Issue or warrant substitution | A warrant with familiar IDs could be paired with altered rivals, falsifiers, or scope. | Issue-to-warrant correspondence is recomputed from the complete records; the plan also binds run, candidate, challenge, evaluator, fixture, observation, and research-ledger digests. | Complete-binding and substitution tests. |
| Question drift | Research prose could change after routing while retaining a stable-looking label. | Each critical question is constructed from one exact rival falsifier and content-addressed; altered content changes or invalidates identity. | Question-tamper and strict-schema tests. |
| Forged current-case question | A self-consistent question with fresh hashes could be injected into a current case even though the exact planner would never generate it. | Current-case plans and transitions require exact membership in the question inventory regenerated from the bound run, ledger, triage, and origin head. Historical cases remain valid against their own immutable bindings. | Forged-current-question and historical-case replay tests. |
| Event-history rewrite | Inquiry history could be overwritten, forked unknowingly, or moved through an illegal lifecycle. | Events form an exact hash chain, publication is atomic and no-clobber, a parent head can be claimed once, and transition legality is checked on replay. | Tamper, lifecycle, explicit-head, and concurrent-publication tests. |
| Chronology reversal | A triage or event could be backdated before the evidence snapshot or human triage that licenses it. | The ledger binds `created_on` and `as_of_date`; triage cannot predate ledger creation; each question binds its triage date; and every event must occur on or after that date. | Ledger-date, triage-date, question-binding, and event-backdating tests. |
| Blocked-route continuation | A valid event type could continue research even after policy blocking or after a criticism was routed to integration. | The CLI enforces an explicit route/event allowlist. `POLICY_BLOCKED` and `INTERNAL_INTEGRATION_REQUIRED` are non-actionable for continued research. | Blocked-route and integration-route append tests. |
| Research chronology deadlock | Requiring a result to pre-exist in the exact ledger that defined its question made honest post-question research impossible; evolving the ledger changed every case and question ID. | A research event now embeds a standalone, strictly parsed v2 source-entry snapshot created after the active question. The frozen ledger supplies background policy; the event enforces dates, provider alignment, primary inspection, exact query/falsifier targeting, and two independent entry digests. | Post-question report lifecycle, unrelated-entry rejection, digest, provider, and date tests. |
| Negative-search confirmation | Claiming to exhaust a bounded query without verifiable execution could be read as support for the survivor. | The active protocol rejects `PROTOCOL_EXHAUSTED`; “not found” leaves the active question open, while agreeing reports cannot promote semantics. | Unsupported-exhaustion and agreeing-report tests. |
| Strength-axis and preservation laundering | A disconnected predicate, inconsistent successor, or local fiber change could be called hardening without an exact baseline, non-broadening, non-vacuity, or protected witness. | The mathematical target separates old-result restriction from role-fiber narrowing and states conjunctive non-broadening, witness, non-vacuity, dependency, and preservation obligations. The current runtime cannot encode all of them, so positive hardening/readiness statuses remain disabled pending schema evolution. | Finite erasure regression plus fail-closed hardening/readiness constructor and parser tests; full model-theoretic obligations remain open. |
| Finite contrast described as a true twin | A two-case fixture that merely admits a grounded case and a labels-only contrast could be overstated as the stronger same-reduct role-relabel twin. | Corpus and report terminology calls it a finite contrast; “twin” is reserved for two theory models with the same declared reduct and different role views under the mathematical target. | Fixture-label, observation, and documentation terminology regressions. |
| Optimizer-disabled guards | Python `assert` could make epistemic or integrity restrictions disappear under `-O`. | Enforcement uses explicit typed failures; the complete suite and persisted-run inquiry are replayed under normal and optimized Python. | Full dual-mode suite and focused invariance tests. |

## Current calibration result

The active record is `forge/runs/SMF-CALIBRATION-CR-1-0-001.4219efce.json`. It is mechanically replayable against the exact local authority bytes and current implementation. It reports `RUN_COMPLETE`, `MECHANICALLY_VALID`, `UNRESOLVED`, `AWAITING_HUMAN`, a null semantic verdict, and `BLOCKED` formalization readiness.

The weak projection admits both the causally grounded fixture and a labels-only contrast case. Adding a disconnected `RoleGrounded` predicate leaves the old-language fixture behavior unchanged under existential erasure, so the naive change is `NO_HARDENING`. These are results about the declared finite fixture and its execution contract only; the pair is not yet the stronger same-reduct role twin required by the mathematical target.

## Deliberately open attack surface

The harness does not determine the semantic loci of a failure, establish that a live assessment is the cause, synthesize arbitrary issue graphs or model deltas, resolve typed human gain/preservation/decision records, prove implicit role determination for a full model class, or validate the source-to-neutral mapping. Primary research bytes are not archived in the ledger; it preserves exact locators and bounded reports. No number of passing regressions closes these gaps.

The next admissible move is therefore plural human triage of the paired fixture. Candidate, auxiliary, test, and scope criticisms may coexist, and one mechanism may cross them. A separate scheduling action may then select one or several compatible dependency-frontier assessments while leaving all others live. Only an external action naming the exact issue-and-warrant target permits falsifier-first research; otherwise the chosen route is internal harness work, internal model work, authority review, or continued suspension awaiting action selection.

Operationally, that triage must be published into the additive lineage and selected by terminal head. An external action must also select exact attack-target IDs from the non-authorizing menu; issue and warrant identity alone do not authorize a question.
