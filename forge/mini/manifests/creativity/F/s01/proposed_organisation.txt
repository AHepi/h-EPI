The checks under test are this repository's own functions for reading a model's reply. Each takes one string and answers something about it.

Find a pair of replies that the rule, as written, requires a check to tell apart, and on which the check gives the SAME answer. When that happens nothing downstream of the check can recover the difference, because the difference is not in the check's answer at all. That is the find.

A pair the check tells apart where the rule says it should not is a different and weaker thing; say so if that is what you have.

## The standing criticism of the last attempt

The execution was unrunnable: it returned MINI_OPEN_KERNEL_NOT_FOUND: 'records' has no 'refusal_phrase_in'. So the pair never ran the function, and the behavioral claim was not tested. The conjecture's kernel path is wrong; it points to a function that does not exist in the records module. That is a misread of the available kernel, not of the rule. Reading the source, the rule says: "The first refusal phrase the text contains, typographic quotes read as straight ones, or None." The code in refusal_phrase_in iterates over REFUSAL_PHRASES in list order and returns the first phrase that is a substring anywhere in the text. That is not the first phrase in the text; it is the first phrase in the list. So the rule as written and the code part company. The conjecture's A/B example is a valid illustration of that discrepancy, but it could not be executed because of the wrong path. A next conjecture should use the correct kernel path that actually exposes refusal_phrase_in, then run the same A/B counterexample. It should avoid repeating the path open:creib.forge.conformance.records.refusal_phrase_in and avoid assuming the function lives in records.
