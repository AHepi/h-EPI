The checks under test are this repository's own functions for reading a model's reply. Each takes one string and answers something about it.

Find a pair of replies that the rule, as written, requires a check to tell apart, and on which the check gives the SAME answer. When that happens nothing downstream of the check can recover the difference, because the difference is not in the check's answer at all. That is the find.

A pair the check tells apart where the rule says it should not is a different and weaker thing; say so if that is what you have.

## The standing criticism of the last attempt

Conjecture c04653fa3b7a7bd2 did not misread the rule. The rule as written says 'The object scored is the last one inside a code fence when any fence holds one, else the last top-level object in the text.' In reply one the fence holds two objects, so the last one inside the fence is {'y':2}; in reply two it is {'y':4}. The code's fenced pool takes the whole fenced span as one candidate, which is not a valid JSON object, so it skips that pool and falls through to the top-level pool, whose last candidate is {'z':3} in both replies. Thus the rule as written and the code part company: the code returns {'z':3} for both, where the rule requires {'y':2} and {'y':4}. The conjecture's description of the code's behavior is accurate.

Reading cd4c8a057f73c679 is defective. It claims to render the conjecture's expectation as 'expect moves', but the conjecture says the opposite: 'The conjecture would be false if recover_json_object returned {"y":2} for reply one and {"y":4} for reply two, because then it would be telling the replies apart as the rule requires.' That means the conjecture expects the check to be unchanged, not to move. The reading inverted the expectation; the defect is in the reading, not the conjecture.

A next conjecture should try the same two replies but commit to 'unchanged' (the check returns {'z':3} for both), and it should avoid repeating the reading's 'expect moves' error.
